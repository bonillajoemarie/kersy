# Kersy — roadmap

**Purpose (owner, 2026-08-15):** a personal cockpit — monitor agents, the workspace, and the task list in ONE layout. Single user (Joe), own machine first (Fedora), portable to Windows/macOS. YAGNI applies hard: no multi-user, no telemetry, no product polish beyond what one person needs daily. If it proves useful, the owner may hand installers to the team — auto-discovery + per-OS installers already cover that; still each user monitoring their OWN machine (no central server).

Stack locked: **Rust + Tauri 2**, core logic in a GUI-free Rust library crate, TypeScript + canvas UI. Each phase = its own spec → plan → implementation cycle.

## Phase 1 — Agent Map (specced: `2026-08-15-agent-map-design.md`)
Live machine-wide monitor: animated force-directed graph of projects → sessions → subagent trees, current tool/shell command per agent, drill-in activity feed, **always-visible task list pane** (from `~/.claude/tasks`), launch-time OS-aware auto-discovery of Claude data roots. Read-only. Installable (RPM/AppImage now; .msi/.dmg from same repo).

## Phase 2 — Workspace shell
Directory browser (Rust fs commands) + **CodeMirror 6** editor (lightweight/fast; deliberately not Monaco) in a split layout; the agent map and task list dock as panes so agents + files + tasks share one window. Read/edit/save, syntax highlighting, fuzzy file open. No AI.

**Memory vault, Obsidian-style (owner, 2026-08-15):** the AI's memory and instructions already live as segregated markdown — per-fact memory files with `[[wikilinks]]` (`~/.claude/projects/<slug>/memory/*.md` + `MEMORY.md` index), and per-repo `CLAUDE.md` / `AGENTS.md` / rule files. Kersy treats these as a vault:
- **Auto-mapping:** the discovery pass finds every memory dir and every `CLAUDE.md`/`AGENTS.md`/`.ai/rules` file across the workspace and links them to their repo/project — no manual vault setup.
- **Graph view:** notes as nodes, `[[wikilinks]]` and file↔repo relations as edges — same canvas/d3-force renderer as the agent map, second mode of the same component (no new subsystem). Broken `[[links]]` shown as ghost nodes, Obsidian-style.
- **Edit in place:** click a node → opens in the CodeMirror pane with wikilink autocomplete against existing note names; frontmatter (type/description) rendered as a header chip.
- Files stay plain markdown on disk in their existing locations — Kersy adds zero storage format of its own; Claude Code keeps consuming them unchanged.

**Integrated terminal (owner, 2026-08-15):** a real PTY terminal pane in the same layout (Rust `portable-pty` backend, `xterm.js` renderer — the standard pairing for Tauri; xterm.js is an accepted, justified exception to the no-framework rule at ~300 KB, loaded lazily only when a terminal is opened). Run anything — builds, tests, or the `claude` CLI itself interactively; sessions started there appear on the agent map like any other. Multiple tabs, working dir follows the file tree selection.

Also: **AI setup manager** (owner, 2026-08-15) — a settings-style screen to see and manage the AI agent tools installed on the machine, not just Claude Code:
- **Claude Code:** MCP servers (user `~/.claude.json`/settings + per-project `.mcp.json`), plugins, skills, agents — list with status, enable/disable, open config in the editor.
- **Other agent CLIs, same treatment where they support it:** Codex CLI (`~/.codex/config.toml` — MCP servers, profiles), Gemini CLI (`~/.gemini/settings.json` — MCP servers, extensions). Detected by the same discovery pass that finds data roots and CLIs (Phase 3 reuses this).
- **Flexible by architecture (owner, 2026-08-15):** one `ToolAdapter` trait covers everything Kersy knows about an AI tool — how to discover it, where its data/config roots live, how to parse its sessions (if supported), how to list/toggle its MCP servers and plugins (if supported), how to drive it headless (Phase 3, if supported). Each capability is optional per adapter, so a new tool can start as "discovery only" and grow. Claude Code is simply the first, most complete adapter; adding another CLI later is one module, never a rework of core or UI (both talk only to the trait). It manages THOSE tools' setups, not Kersy's own (Kersy has no plugin system of its own — decided against for lightweightness). Config-file read/write only, no new subsystem.
- (Possible later extension, not committed: monitoring other agents' session logs — e.g. `~/.codex/sessions` — on the map alongside Claude's. Needs its own format research first.)

## Phase 3 — AI prompt, multi-model

**No-gap principle (owner, 2026-08-15):** existing GUIs for Claude Code are weaker than the CLI because they reimplement a subset. Kersy closes that gap by never reimplementing: the model interface is a GUI *over the genuine CLI process* (headless/stream-json), so 100% of CLI capability — skills, MCP, subagents, hooks, permission modes/plan mode, session resume, slash commands — is available by construction, and new CLI features surface in Kersy the day the CLI updates. Kersy's UI job is presentation and control (streaming output, permission prompts as dialogs, session/agent visualization on the map), never capability emulation. Anything the GUI can't express yet gets a raw passthrough (type any CLI flag/slash command), so the GUI is a superset in usability and never a subset in power.

**Routines (owner, 2026-08-15):** scheduled recurring agent runs, like Claude Code's routines feature. Create/edit/list/pause in a routines screen: name, prompt (or slash command), working directory, provider/model, schedule. Execution is delegated to the **OS scheduler** (systemd user timers on Linux, launchd on macOS, Task Scheduler on Windows) invoking the agent CLI headless — so routines fire even when Kersy is closed and Kersy stays 0%-idle (no daemon of its own). Each run writes normal transcripts, so finished and live routine runs appear on the agent map automatically, badged as routine-triggered, with run history from the same data. Kersy also lists routines the tools manage themselves (e.g. Claude Code cloud routines) read-only via their configs, per the no-gap principle.

Chat pane with a two-lane provider layer:
- **Subscription lane (default):** drive locally installed agent CLIs headless — Claude Code (`claude -p` / Agent SDK, existing Team-plan login), Codex CLI (ChatGPT plan), Gemini CLI. Detected in the same discovery pass as data roots; appear in the model picker automatically. Sessions launched this way write to `~/.claude/projects`, so they appear live on the agent map — prompt and monitor form one loop.
- **Key lane (optional):** direct Anthropic/OpenAI APIs; keys in OS keychain. Never required.
- **Local lane — offline lightweight models (owner, 2026-08-15):** a built-in local-models screen: browse the Ollama library, see installed models with disk size, **download (pull with progress), delete, and chat with them fully offline** from the same prompt pane. Local models are first-class providers, not a chat-only toy: anything an agent does through the provider seam (Phase 3 prompt pane, Phase 4 agent-mode acting on the workspace) can run on a local model — pick it in the model picker like any other. Implemented by driving Ollama's local HTTP API (detected like the other CLIs; friendly install pointer if absent) — Kersy never embeds an inference engine, keeping the binary small. Exposed through the same `ToolAdapter`/provider seam, so another local runtime (e.g. llama.cpp server, LM Studio) is one adapter later.
